# UI/UX 全面改修デザイン依頼書

本書は、**Tessera** の UI/UX を **このプロジェクトを初めて見るデザイナーに、0 から設計してもらうための依頼書** である。

依頼先は、現在の画面、既存のデザイン、過去の設計判断を知らない前提とする。既存 UI をベースにした微修正ではなく、プロダクト価値、ペルソナ、利用シーン、維持すべき機能要件から、SP / PC それぞれに最適な体験を再設計してほしい。

ただし、すでに実装済みの機能はプロダクトの要件として存在する。画面構成、見た目、情報設計、操作導線は自由に再設計してよいが、現在提供している主要機能を削ったり、到達不能にしたりしないこと。

## 依頼先の前提

この依頼は、あえて本プロジェクトを触ったことのない人に行う。

そのため、以下を前提にする。

- 現在の UI を踏襲する必要はない
- 現在のレイアウト、色、余白、ナビゲーション、コンポーネント構造に引っ張られなくてよい
- 既存画面のスクリーンショットを前提にしない
- リポジトリ内部の実装詳細を知らなくても、この文書だけで設計意図を理解できる状態を目指す
- 機能一覧は「残すべき要件」であり、「今と同じ画面に置くべき」という意味ではない
- SP 画面と PC 画面は大きく異なってよい

## 依頼の目的

AI で情報処理するだけで終わらせず、学習内容を記憶として定着させる体験を、画面全体で一貫して伝える。

今回の改修は、部分的な見た目調整ではなく **全面的な UI/UX 再設計** とする。

求めたいのは、現在の画面をきれいにすることではない。学習者が「メモを残す」「AI 候補を確認する」「カードとして採用する」「復習で思い出す」という行動を自然に続けられるように、プロダクト体験そのものを組み直すことである。

制約として、現在動いている機能、データ構造、主要導線、権限制御、API 連携は壊さない。

## プロダクト概要

**Tessera** は、AI 策問補助付きのフラッシュカードアプリである。

名称は、「学び」「メモ」「AI」を組み合わせたもの。子供にも親しみやすく、学習メモから AI がカード候補を作る価値を直感的に伝える。大人の資格学習や技術学習でも使えるよう、かわいさに寄せすぎず、やさしく信頼できる学習ツールとして見せたい。

ユーザーは、学習中に得た知識や間違えた論点を短いメモとして残す。AI はそのメモをもとに、フラッシュカード候補を複数生成する。ユーザーは候補を確認し、必要に応じて編集し、採用する。採用されたカードは、間隔反復により復習対象になる。

重要なのは、AI が生成したものを自動で学習済みにしないことである。AI は「策問補助」であり、最終的にカードとして残すかどうかは人間がレビューする。

### 中心価値

- メモから問題を作る手間を減らす
- AI 生成を、人間レビューによって学習に使える品質にする
- 復習スケジュールに乗せて、記憶として定着させる
- 学習者が「読んだだけ」「AI に聞いただけ」で終わらない状態を作る

### 中心体験

**メモを書く → AI が候補を出す → 迷わず採用する → 翌日ちゃんと復習に出る**

## 用語

外部デザイナーが最初に理解すべき用語を整理する。

### メモ

学習中に得た知識、間違えた論点、読書・講義・業務で得た気づきの断片。まだ復習に適した「問い」にはなっていない素材。

### AI 候補

メモをもとに AI が生成したフラッシュカード候補。まだ正式なカードではない。ユーザーが確認し、採用したものだけが復習対象になる。

### カード

採用済みのフラッシュカード。問題、答え、補足説明などを持つ。間隔反復の対象になる。

### デッキ

カードを学習分野や目的ごとにまとめる単位。階層構造を持てる。

### 分野テンプレート

AI にどのような観点でカード候補を作らせるかを指定する策問方針。例: 資格試験向け、技術概念向け、比較理解向け。

### 復習

カードの問題を見て答えを思い出し、Again / Hard / Good / Easy で自己評価する行為。評価に応じて次回出題日が決まる。

### 間隔反復

忘れそうなタイミングで再出題する学習方式。ユーザーが毎回全カードを見返さなくても、必要なカードが今日の復習として出る。

## 最優先ペルソナ

最優先は **資格勉強中のビジネスパーソン** とする。

このペルソナは、試験日、出題範囲、合格ライン、限られた学習時間という制約が明確であり、以下の主要価値がそのまま成果に結びつく。

- 間違えた論点や重要箇所を短時間でメモする
- AI がカード候補を生成する
- ユーザーが候補を確認して採用する
- 今日の復習を終える
- 試験日や弱点を意識して進捗を確認する

副次的に、**エンジニアなどの知的技術職** も重視する。Markdown メモ、技術記事、設計判断、障害対応メモからカードを作る体験は、本プロダクトの独自性と初期検証に重要である。

## 改修方針

### 1. 既存 UI を前提にしない

今回の依頼では、現行画面の構成を正解として扱わない。

避けたいこと:

- 既存画面のカード、ボタン、余白、色だけを整える
- 現在のナビゲーションをそのまま残す前提で考える
- PC 画面を縮小して SP 画面にする
- 既存コンポーネント単位に合わせて画面を分割する
- 開発しやすさだけで体験を決める

期待すること:

- ペルソナの利用シーンから情報設計を組み直す
- SP と PC を別々のプロダクト体験として設計する
- ユーザーの主要行動を起点に画面を再構成する
- 現在の機能は維持しつつ、配置や見せ方は再設計する
- 「学習内容を記憶として定着させる」という目的から逆算する

### 2. 現在の機能を損なわない

画面構成や見た目は大きく変えてよい。ただし、現在提供している操作、状態、エラー処理、権限、ショートカット、アクセシビリティを消さない。

既存 UI を置き換える場合も、同等以上の機能を新 UI に移植する。

機能一覧は、現行 UI の模写指示ではない。新しい画面において、同じ目的がより自然に達成できるなら、画面分割、導線、名称、優先順位は変えてよい。

### 3. 全面的な改修として扱う

局所的な色変更やカード装飾ではなく、以下をまとめて見直す。

- 情報設計
- 画面遷移
- ナビゲーション
- レイアウト
- タイポグラフィ
- 色
- 余白
- CTA の優先順位
- 空状態
- ローディング
- エラー表示
- モバイル操作
- PC キーボード操作

### 4. SP と PC は大きく異なってよい

SP と PC で同じレイアウトを縮小・拡大する必要はない。利用シーンが異なるため、体験を分けて設計する。

SP は、通勤中、昼休み、寝る前などの短時間利用を想定する。片手操作、即メモ、今日の復習、候補の高速採用を優先する。

PC は、まとまった学習、メモ整理、候補レビュー、カード編集、デッキ整理を想定する。情報密度、複数ペイン、キーボード操作、検索性を優先する。

### 5. デザイン案には根拠を添える

外部デザイナーには、単に画面を作るだけでなく、主要な設計判断の理由も示してほしい。

例:

- なぜ SP ではこのナビゲーションにしたか
- なぜ PC ではこのペイン構成にしたか
- 候補レビューで採用ボタンをどこに置いた理由
- 復習中に表示する情報を絞った理由
- 初回利用者が最初の成功体験に到達するまでの設計意図

## 体験コンセプト

**「学習メモを、今日覚えるべき問いに変える作業台」**

ただの AI 生成ツールではなく、以下の循環を自然に回せる学習プロダクトとして設計する。

1. メモを書く
2. AI が候補を出す
3. 人間がレビューして採用する
4. 復習で思い出す
5. 進捗と弱点を見て次の学習へ進む

## 主要体験フロー

### フロー A: 資格学習の短時間フロー

1. 問題集や講義で間違えた論点をメモする
2. 保存して AI 候補生成へ進む
3. 候補を 3〜5 件確認する
4. 必要な候補だけ採用する
5. 翌日以降、今日の復習に出る

このフローは SP で最短化する。画面遷移や入力項目を増やしすぎない。

### フロー B: PC での候補レビュー集中フロー

1. メモ一覧から未生成または候補未レビューのメモを開く
2. 左にメモ本文、右に AI 候補を表示する
3. キーボードまたは明確なボタンで採用 / 編集 / 却下する
4. 採用先デッキとタグを調整する
5. 次の未処理メモへ移動する

このフローは PC で情報密度を上げてよい。

### フロー C: 毎日の復習フロー

1. ダッシュボードまたは SP ホームから今日の復習を開始する
2. 問題を見る
3. 答えを見る
4. Again / Hard / Good / Easy で評価する
5. 完了後、今日の成果と次回予定を見る

復習画面は集中を妨げない。余計な統計や管理機能を前面に出さない。

## 画面別デザイン要件

### 1. ランディングページ

目的:

- 公式リリースと収益化を見据え、第一印象を改善する
- 「AI で要約するアプリ」ではなく「記憶に定着させるアプリ」と伝える

要件:

- ブランド名と価値がファーストビューで明確である
- AI 候補生成、レビュー、間隔反復の流れが一目で分かる
- ログイン導線を維持する
- 将来的に料金、利用例、FAQ を足せる余白を持つ

### 2. ログイン / オンボーディング

目的:

- 初回利用者が、何をすれば価値を感じられるか迷わない

要件:

- ログインフォームを維持する
- オンボーディングで学習目的、試験名、既定テンプレートなどを設定できる状態を想定する
- 初回成功体験は「最初のメモから最初のカード候補を作る」ことに寄せる

### 3. ダッシュボード / ホーム

目的:

- ユーザーに「今日やること」を返す

要件:

- 最上位 CTA は「今日の復習」または「メモを書く」にする
- 未レビュー候補がある場合は明確に表示する
- 今日の復習数、復習遅れ、最近のメモ、最近のカードを維持する
- AI 使用量 / コストは表示するが、主役にしすぎない
- 資格ペルソナ向けに、試験日までの日数を将来追加できるレイアウトにする

SP:

- ホームは「今日の復習」「メモを書く」「未レビュー候補」の 3 つを中心にする
- 数字は大きく、カード数や補助統計は折りたたみでもよい

PC:

- 2〜3 カラム構成を許容する
- 今日のタスク、最近のメモ、最近のカード、統計を同時に見られるようにする

### 4. メモ入力

目的:

- 学習中の知識断片を、最短で保存して AI 生成へ送る

要件:

- Markdown 入力とプレビューを維持する
- 分野テンプレート、サブ分野、学習目的、補足コンテキストを維持する
- 「保存」と「保存して候補生成」を維持する
- 詳細設定は必要な時だけ開ける
- 保存失敗時のエラーと成功 toast を維持する

SP:

- 本文入力を画面の主役にする
- アクションは下部固定にする
- 詳細設定はボトムシートや折りたたみでもよい
- キーボード表示時に CTA が隠れない

PC:

- 本文入力とプレビューを左右分割してもよい
- テンプレートや詳細設定は右ペインに置いてよい
- `Cmd/Ctrl + Enter` を維持する

### 5. AI 候補生成

目的:

- AI 生成を待つ不安を減らし、生成条件と結果を理解しやすくする

要件:

- 生成、追加生成、再生成を維持する
- 生成ステータス、生成中表示、partial success、失敗時メッセージを維持する
- 分野テンプレート選択を維持する
- 候補数や生成モードを将来追加できる余白を持つ

SP:

- 生成 CTA を大きく、状態表示を短くする
- 長いメモ本文は折りたたむ

PC:

- メモ本文、生成条件、候補一覧を同時に見られる構成が望ましい

### 6. 候補レビュー

目的:

- AI 候補を「使えるカード」に変換する

要件:

- 候補の編集、採用、却下、復元、一括採用を維持する
- 採用先デッキ選択を維持する
- カード種別、focus type、confidence、AI 判断理由を維持する
- 採用済み、却下済みの状態表示を維持する
- Undo toast を維持する

SP:

- 1 候補ずつ集中して判断できるカード UI にしてよい
- 採用、編集、却下は親指で押しやすい位置に置く
- デッキ選択はボトムシートでもよい

PC:

- 一覧性を重視し、複数候補を比較しやすくする
- 未処理候補と履歴候補を分ける
- キーボード操作を前提にした状態設計を行う

### 7. カード一覧 / カード詳細

目的:

- 作成済みカードを探し、編集し、整理できるようにする

要件:

- 検索、デッキ絞り込み、タグ絞り込みを維持する
- 学習中 / アーカイブ済み切り替えを維持する
- 無限スクロールを維持する
- カード作成、編集、詳細表示を維持する
- cloze-like 表示を維持する

SP:

- フィルタはコンパクトにまとめる
- 検索を優先し、詳細フィルタは展開式でよい

PC:

- 左にフィルタ、右にカード一覧などの構成を許容する
- 検索と絞り込みは常時見えていてよい

### 8. デッキ / タグ / テンプレート

目的:

- 学習対象を整理する。ただし整理作業が学習の主目的にならないようにする

要件:

- デッキ階層ツリーを維持する
- DnD による並び替えと親子変更を維持する
- デッキ作成、編集、詳細を維持する
- タグ作成、削除を維持する
- テンプレート作成、編集を維持する

SP:

- DnD の説明や操作は簡潔にする
- 深い階層操作は無理に主役にしない

PC:

- デッキツリー、カード一覧、詳細を複数ペインで見せてもよい
- DnD 操作の affordance を明確にする

### 9. 復習

目的:

- 記憶定着の中核体験を、毎日続けられる軽さにする

要件:

- 問題表示、答え表示、評価ボタンを維持する
- Again / Hard / Good / Easy を維持する
- 進捗表示を維持する
- セッション完了表示を維持する
- 追加復習モードを維持する
- アーカイブを維持する
- キーボード操作とハプティクスを維持する
- フリップ表示を維持する

SP:

- 画面を復習カードに集中させる
- 評価ボタンは下部固定にする
- Again / Hard / Good / Easy は誤タップしにくいサイズにする
- スワイプ評価を将来追加できる余白を持つ

PC:

- カードを中央に配置し、キーボード操作のヒントを自然に表示する
- 評価ボタンは横並びでもよい
- 長文カードでも読みやすい幅にする

### 10. 統計 / 設定 / 管理

目的:

- 学習を継続するための状態確認と、運用設定を行う

要件:

- 復習統計を維持する
- ユーザー設定を維持する
- AI プロバイダ / モデル設定を維持する
- 管理者向けユーザー作成とシステム設定を維持する
- 管理者専用メニューの表示条件を維持する

SP:

- 統計は要約中心にする
- 詳細グラフや管理機能は階層を深くしてよい

PC:

- 表形式、設定グループ、管理者向け詳細情報を見やすく整理する

## ナビゲーション要件

### SP

SP は PC と大きく異なる体験にしてよい。

維持する主要導線:

- ホーム / ダッシュボード
- メモ
- 復習
- デッキ
- その他
- 最頻アクションへのショートカット

設計方針:

- 現行実装はボトムタブと FAB だが、これに固定しない
- 片手操作で主要導線に到達できるなら、タブ、ホーム中心、アクションシート、専用ホームなど別案でもよい
- 最頻アクションは「メモを書く」または「今日の復習」とする
- 復習中や入力中など、下部固定 CTA と競合する画面では補助アクションを出しすぎない
- 片手操作を優先する
- 画面下部の safe-area を必ず考慮する

### PC

維持する主要導線:

- ダッシュボード
- メモ
- 復習
- デッキ
- カード
- テンプレート
- タグ
- 統計
- 設定
- 管理者メニュー

設計方針:

- 現行実装は左サイドバーだが、これに固定しない
- 学習、整理、運用の導線が分かりやすければ、サイドバー、トップナビ、コマンドパレット中心、複合型など別案でもよい
- 情報密度を上げてもよい
- 将来的な Cmd/Ctrl + K コマンドパレットに接続しやすい構造にする

## ビジュアル方向性

### 目指す印象

- 落ち着いている
- 学習に集中できる
- 信頼できる
- AI らしさはあるが、過度に派手ではない
- 資格学習にも技術学習にも耐える

### 避ける印象

- AI ツールのように派手すぎる
- 学習管理アプリとして硬すぎる
- カードや枠が多すぎて情報が散らかる
- PC 画面をそのまま SP に縮小したような画面
- 装飾が主役になって復習や入力を邪魔する

### 参考方向

- Linear: 整った情報密度、落ち着いた洗練感
- Notion: 入力しやすさ、柔らかい整理感
- Superhuman: キーボード駆動、効率の高さ
- Quizlet / Anki Mobile: 復習カード体験
- Duolingo: 継続の軽い報酬感。ただし本アプリでは過度なゲーム化は避ける

## 受け入れ基準

- 現在実装済みの主要機能が失われていない
- SP と PC がそれぞれの利用文脈に最適化されている
- SP で主要操作が片手で完結する
- PC で主要操作がキーボード中心に扱える
- メモ入力から AI 候補生成までの導線が短い
- 候補レビューで採用 / 編集 / 却下が迷わない
- 復習画面でカードに集中できる
- 今日やるべきことがダッシュボードで分かる
- loading / empty / error / success 状態がデザインされている
- 44px 以上のタップターゲット、focus-visible、aria 属性などのアクセシビリティを損なわない
- 管理者専用機能や設定機能が見落とされていない

## 実装時の注意

- `frontend/src/app` はルーティング層に留め、ビジネスロジックを置かない
- Feature-Sliced Design の依存ルールを守る
- shadcn/ui は直接改造せず、必要に応じて拡張する
- SP / PC の分岐は Tailwind の responsive class またはコンポーネント分割で扱う
- 既存の TanStack Query hook、FormRequest、API エンドポイントとの整合を維持する
- AI 候補は自動採用しない。必ず人間レビューを通す
- 復習スケジュールに影響する操作と、追加閲覧モードのように影響しない操作を UI 上で区別する
